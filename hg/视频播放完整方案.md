## 配套文件

| 文件 | 说明 |

在 Debian 主机运行，工作目录为脚本所在目录：

```bash
# 完整接口对照 + CDN 检查，自动读取当前签名 App 的设备资料
python3 hg_video_check.py --server http://127.0.0.1:8901 \
  --device-from-container hongguo-signer-native

# 搜索 → 详情 → 播放模型 → 完整下载 → 完整音视频解码
# --decode 需要 ffprobe / ffmpeg；当前加密样本会返回 4，不会误报成功
python3 hg_video_check.py --server http://127.0.0.1:8901 \
  --device-from-container hongguo-signer-native --mode chain \
  --download /tmp/hg-sample.mp4 --decode

# 导出设备资料，供其他主机请求同一个签名服务时使用
python3 hg_video_check.py --server http://127.0.0.1:8901 \
  --device-from-container hongguo-signer-native \
  --save-device-profile /tmp/hg-device-profile.json --mode chain

python3 hg_video_check.py --server http://192.168.3.83:8901 \
  --device-profile /path/to/hg-device-profile.json --mode chain

# 指定单集和剧集，不重新搜索
python3 hg_video_check.py --server http://127.0.0.1:8901 \
  --device-from-container hongguo-signer-native --mode chain \
  --vid 7611102984516160574 --series-id 7611100992238521406
```

`--device-from-container` 只临时附加当前 App，读取 `NetworkParams.addCommonParams()`，不会启动界面或改容器属性。它复用签名容器已有的 Frida，主机无需安装 Frida。导出的 JSON 只保留设备/应用参数和 User-Agent，权限为 `0600`，不含签名、会话令牌或播放地址。App 重装、清数据或更换设备后应重新导出。

退出码：

| 代码 | 含义 |
|---|---|
| `0` | 所选模式检查通过；只有 `--download --decode` 通过才代表完整音视频解码通过 |
| `1` | 视频接口、网络或 CDN 检查失败 |
| `2` | 签名服务、设备资料或命令参数不可用 |
| `3` | 搜索失败或没有短剧结果 |
| `4` | 下载地址可用，但加密视频尚未验证可播放 |
| `5` | 文件大小、文件轨道或普通解码检查失败 |

## 1. 签名服务

### 1.1 接口

```
GET  http://<host>:8901/health     健康检查（会真实签一次名）
GET  http://<host>:8901/info       环境信息
POST http://<host>:8901/sign       生成签名头
POST http://<host>:8901/verify     搜索接口自检（不含播放）
```

### 1.2 `/sign` 请求/响应

```bash
curl -X POST http://123.57.172.104:8901/sign \
     -H 'Content-Type: application/json' \
     -d '{"url":"https://api5-normal-sinfonlineb.fqnovel.com/reading/bookapi/search/tab/v?aid=8662&query=test"}'
```

```json
{
  "X-Gorgon": "840460274485...",
  "X-Khronos": "1793844276",
  "X-Argus": "G/fqag==",
  "X-Ladon": "AAAOAA==",
  "X-Medusa": "Nu3qah6mpaB6mOcp...",
  "X-Helios": "5WdzAIgW1mkozQ0f..."
}
```

### 1.3 签名与 URL 的绑定规则（实测）

| 维度 | 结论 |
|---|---|
| 绑定 path | 是 |
| 绑定 **全部** query 参数（含 `_rticket`） | 是 |
| 绑定 host | **否**（sinfonlinea ↔ b 互换仍有效） |
| 有效期 | **> 1 小时**（实测 61.8 分钟后仍有效） |
| 字节完整性 | 全字节校验，任意改动即失效 |

**因此**：每次请求必须先构造完整 URL → 再签名 → 再发送。不能预先签名复用不同 URL。

### 1.4 各接口需要的签名头（设备资料一致时）

以下是 Debian 上更新脚本的对照结果；每个请求均先构造完整 URL 再签名。

| 签名头组合 | `search/tab` | `video_detail` | `video_model` |
|---|---|---|---|
| 无签名 | 0 字节 | 0 字节 | 0 字节 |
| `Medusa + Helios` | 54,748 字节 / code=0 | 95,942 字节 / code=0 | 6,784 字节 / code=0 |
| Gorgon 四个 | 0 字节 | 0 字节 | 0 字节 |
| 全 6 个 | 54,754 字节 / code=0 | 95,952 字节 / code=0 | 6,780 字节 / code=0 |

本次样本仅带 `Medusa + Helios` 即可通过三个接口。默认仍带全 6 个头。早期在设备 ID 不匹配时 `video_model` 所有组合都空，不能据此排除设备身份或签名上下文问题。


**关键点**

1. `video_model` 常为**字符串**，必须 `json.loads()` 二次解析；也兼容直接返回对象
2. 响应里的 `video_id`（`v02ebeg...`）是 CDN 内部 ID，**与搜索返回的 `vid`（纯数字）不是一回事**
3. `main_url` 是完整 mp4 直链，自带签名参数（`ft=`、`feature_id=`、`l=`、`n80_tk=`）
4. 有效期由 `url_expire` 控制，实测约 **6 小时**
5. **`video_model` 必须用 `vid`，不能用 `series_id`** —— 用 `series_id` 会返回 `code=101113 CHAPTER_INFO_GET_ERROR`
6. 必须检查每个 `video_list[]` 的 `encrypt_info`；这次所有清晰度均标记 `encrypt=true`、`encryption_method=cenc-aes-ctr`，不能直接交给普通播放器播放
7. 短剧样本可省略 `video_platform`，或使用搜索结果的 `video_platform=3`；不要套用 UGC 调用方的 `2`

### 3.4 步骤 4：下载与播放验证

```bash
curl --fail --output sample.mp4 "<main_url>"
ffprobe -v error -show_format -show_streams -of json sample.mp4
ffmpeg -v error -xerror -i sample.mp4 -map 0:v:0 -map '0:a:0?' -f null -
```

本次 CDN 请求无需额外签名头或鉴权头，完整文件大小与 `video_meta.size` 一致。但模型中的 `encrypt_info` 表明下载内容经过加密：

```json
{
  "encrypt": true,
  "encryption_method": "cenc-aes-ctr",
  "kid": "<模型中的标识>",
  "spade_a": "<模型中的播放器加密信息>"
}
```

`ffprobe` 能识别 MP4、HEVC 和 AAC 轨道，不代表媒体数据可解码。本次 `ffmpeg -xerror` 返回 183，出现 `Invalid NAL unit size` 和 AAC 错误。播放端需要使用能处理该加密模型的播放器；仅取得 `main_url` 不足以完成播放。

## 4. Debian 实测：已定位问题与剩余边界

### 4.1 验证环境与原始复现

- 时间：2026-11-05，约 11:12–11:31（UTC+8）。
- Debian 13：`192.168.3.83`。
- 签名容器：`hongguo-signer-native`，HTTP `127.0.0.1:8901`。
- Android 容器：`hongguo-android-native`，机型 `redroid14_x86_64_only`。
- App：`com.phoenix.read`，版本 `7.3.9.32`，Frida `16.4.10`。

原脚本 `--mode all` 的退出码为 1：搜索正常、详情 73 集，播放模型在 10 组参数下均为 HTTP 200 / 0 字节。

### 4.2 根因：设备 ID 与签名 App 不匹配

对同一单集 `7611102984516160574`、同一签名服务，保留旧脚本的其他参数：

| 只替换哪些字段 | 播放模型结果 |
|---|---|
| 全部保持旧示例 | HTTP 200，0 字节 |
| `device_id` | code=110，`ILLEGAL_ACCESS` |
| `iid` | 0 字节 |
| `cdid` | 0 字节 |
| **`device_id + iid`** | **code=0，5,501 字节，取得地址** |
| `device_id + iid + cdid` | code=0，5,550 字节，取得地址 |
| 仅机型、品牌、语言、分辨率等 | 0 字节 |
| 仅补充 App 的其他请求参数 | 0 字节 |

这证明本次失败的关键是 URL 中的设备 ID 配对，而不是必须将 redroid 机型伪装成三星。更换全部 App 请求头也不能修复旧设备 ID 的空响应；成功请求不需要额外 Cookie，不需要先进入短剧播放页。

`/sign` 本身继续接收 `{"url": "完整 URL"}` 并返回 6 个头即可。调用端必须使用当前签名 App 的设备资料。后续如扩展 `/info` 返回设备资料可简化远程调用，但不是本次修复的必要条件；本次未修改签名服务。

### 4.3 第二个问题：不能套用 UGC 的 platform=2

抓取 `VideoRecBookDataHelper.f(vid)` 的 App 请求后，确认它会填 `video_platform=2`。这是 UGC 视频场景，不能直接作为短剧接口的标准请求。

使用一致的设备资料后：

| 参数 | 结果 |
|---|---|
| 仅 `video_id + source=0` | code=0，返回地址 |
| `video_platform=2` | code=101116，`SERVICE_ERROR` |
| `video_platform=3` | code=0，返回地址 |
| `need_all_video_definition=true` | code=0，返回多清晰度 |
| `device_level=3`、`video_id_type=0`、`source=1/2` | 本次样本均 code=0 |

旧测试中因为所有组合都带错设备 ID，参数差异被空响应掩盖，不能得出“已经确认不是参数问题”的结论。

## 5. 可运行实现

以配套的 `hg_video_check.py` 为准。旧文档内嵌代码使用了其他模拟器的固定设备 ID，已移除，避免继续复制错误配置。

脚本处理顺序：

1. 检查 `/health`、`/info`，读取当前签名 App 的设备资料。
2. 构造完整 URL，每个请求单独调用 `/sign`，核对 6 个签名头。
3. 搜索取得单集和剧集 ID，详情读取 `dir_data.item_list[].video_id`。
4. 解析字符串或对象形式的 `video_model`，检查播放地址、媒体信息及加密标记。
5. CDN 仅限量读取开头 1KB，检查 HTTP 状态、Range 和 `ftyp`，防止错误页误报为 MP4。
6. 启用 `--download` 时校验完整文件大小并输出 SHA256；启用 `--decode` 时使用 FFprobe 和 FFmpeg 解码完整音视频。
7. 加密流未通过解码时返回 4；网络、签名、搜索和文件错误分别返回相应退出码。

### 8.1 `VideoRecBookDataHelper.f()` 的真实构造（重要）

```java
public static Observable f(String str) {
    GetVideoModelRequest req = new GetVideoModelRequest();
    req.videoId = str;
    req.videoPlatform = VideoPlatformType.UgcVideo;      // = 2

    DeviceLevel level = DeviceLevel.High;                 // = 3
    if (NsUtilsDepend.IMPL.isLowDevice())         level = DeviceLevel.Low;
    else if (NsUtilsDepend.IMPL.isMiddleLowDevice()) level = DeviceLevel.Middle;
    req.deviceLevel = level;

    SeriesResolutionABValue ab = SeriesResolutionABValue.a.a();
    req.needAllVideoDefinition = ab.requestAllDefinition;
    req.needMp4Align          = ab.requestMp4Align;

    return c.f().getVideoModelRxJava(req).subscribeOn(Schedulers.io());
}
```

**这是 UGC 视频调用方的构造方式。** 对本次短剧 `vid`，`video_platform=2` 会返回 `SERVICE_ERROR`。短剧最小请求可省略此字段，或按搜索结果使用 `3`。不要把这个方法的参数直接套用到短剧流程。
